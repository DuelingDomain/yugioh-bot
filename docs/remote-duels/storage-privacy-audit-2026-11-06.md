Code review of `feat/remote-undo-once`, starting at `0656f0290`. No production configuration, database, media server or logs were inspected. Paths are relative to this worktree. This audit includes the retention and upload-gate fixes from that review. The retention section below is updated for the owner decision of 7 November 2026; historical validation is recorded at the end.

## Retention and room closure

Owner decision, **7 November 2026**: started Remote Duels, match history and board-state replays are kept **with no time limit by default**. `REMOTE_DUELS_RETENTION_DAYS` unset, empty or `0` means indefinite retention; positive whole days are an optional cap. The example is `0`. Existing deployments explicitly set to `1` or another positive value must clear it or set `0` to adopt this policy. Negative, fractional, invalid and unsafe values fail validation. Without a cap, abandoned ended lobbies that never started are deleted after one day. With a cap, ended rooms older than that window are deleted. The cutoff is strict; active rooms and rooms exactly at the cutoff stay.

The hourly worker drains eligible room deletions in transactions of at most 100, rather than one batch per hour. The ended-room partial index and phone bucket room index support selection/cleanup. The hourly schedule remains in `packages/worker/src/index.ts`; policy is in `packages/shared/src/services/remote-retention.ts`, re-exported by the worker.

History needs `remote_tables.state_json`, metadata, human/bot seats and registered deck snapshots. `replayFrames` reads the ordered `remote_events` log and resolves its `facts_hash` values. `remote_values` contains immutable replay facts and Undo board positions, not camera or vision blobs; `remote_state_values` owns the positions referenced from room state. All these remain while a started duel is retained. Account deletion still removes the affected rooms and their unshared values.

There already is an idle end: `REMOTE_IDLE_WARNING_MS` is eight minutes, `REMOTE_IDLE_CLOSE_MS` is ten minutes, and `sweepIdle()` sets `status='ended'`, `ended_at` and `end_reason='idle'`. `packages/ws/src/server.ts` calls it every 30 seconds when Remote Duels is enabled. Actions and seated-player `touch()` calls refresh activity; spectators do not. Leaving the creator's lobby also ends it. Disconnecting everyone does not end it immediately: without further activity, the sweep ends it after ten minutes. A recently started room gets at least ten minutes. Closure depends on the WS process running its sweep; the worker's retention job does not itself close rooms.

An optional capped purge or abandoned-lobby purge deletes the room and its phone rows in one writer transaction. Existing room triggers/cascades delete seats, bot seats, events, spectators and state-value references; value collectors delete facts/Undo positions once no other room references the same content hash. A value legitimately shared with another room remains for that room.

Transient data is not retained with history: the hourly worker removes phone pairs/modes/attempts and spectator slots/tabs/admin watches for ended tables. The web media janitor lists LiveKit rooms every 30 seconds and deletes `remote-<slug>` / `remote-<slug>-voice` rooms whose SQL room is missing or ended more than 15 minutes ago. This retains the existing media grace while releasing webcams, phones, spectators and optional voice independently of SQL history. Failures and recreated rooms are discovered again on later ticks; media teardown depends on the web janitor and LiveKit being available. There are no separate remote voice or recording-session tables. Global AI rate-limit rows have no room association: the worker expires those after their hour window. Pairing attempts expire after five minutes and are also swept hourly; old buckets without a room association are discarded. Presence cleanup remains unchanged at 24 hours without a heartbeat.

Remote Duels can select an existing `saved_decks` row. Its columns are `id`, `guild_id`, `owner_user_id`, `name`, `mode`, `deck_json`, `created_at`, `updated_at`; later deck features add their own general-purpose metadata. This is the user's reusable saved deck, not a retained Remote Duel. Deleting a room deletes the registered snapshots, not the reusable deck. Account deletion removes the user's saved decks.

General account/presence and explicit bug reporting are separate app storage. Presence writes `users.last_seen_at`, `last_route`, `online_since` and expires after 24 hours; route categories are normalized (`packages/shared/src/presence/routes.ts`). A submitted bug report can keep user-written card/user information in `bug_reports.description`, `expected`, `context_json`, `submitter_json`, `diagnostics_json`, `path`, `duel_slug` and its identity/issue fields (`packages/shared/src/services/bug-reports.ts`). This is an explicit report, not automatic camera collection; the report API has no image attachment field. Room purge does not delete general accounts, reusable decks or bug reports.

## Images, video and on-disk paths

**Video:** all four `services/livekit/*` files were read. They configure LiveKit server containers and a read-only YAML mount; no egress/ingress/recording service, recording storage volume or egress configuration exists. There is no `EgressClient`, recording-start call or `MediaRecorder` in the Remote Duels runtime. LiveKit relays camera tracks and data packets. Phone-to-desktop JPEG packets and recognition guesses are transient data packets; their server code does not write image files. This is a code/configuration finding, not verification of a running media server.

**Feedback JPEGs:** `packages/shared/src/services/vision-feedback.ts` writes `<DATA_DIR>/vision-feedback/<uuid>.jpg`; absent `DATA_DIR`, the directory is next to the SQLite file (or the service's documented `data` fallback). `POST /api/remote-vision/feedback` and the service require `REMOTE_VISION_FEEDBACK=1`. Ordinary users must opt in; owner accounts default to sharing on when collection is enabled. JPEG input is at most 32 KiB, 224 pixels wide and 400 pixels high, then re-encoded without metadata. The API expects a card crop but verifies image format/dimensions, not the absence of faces or other content. Do not promise that arbitrary accepted images cannot contain a face or a resized full view. Approved/two-user-supported embeddings and confusion statistics can be served to players without contributor IDs; the JPEGs are not served through that learning API.

**Local field diagnostics:** `POST /api/remote-vision/diagnostics` writes `<VISION_DATA_DIR>/diagnostics/field/<timestamp>-<uuid>.jpg` and `.json`; the fallback root is `../../data/vision` from the web process. JPEGs are at most 32 KiB and 224×384. JSON includes time, suggested card IDs/names/scores, reason, zone, quads, deck/seen/voice/frame-class priors, runtime/backend, quality and timings. It retains the latest **24 image/JSON pairs**, with **no age limit** and no per-user deletion hook. The route requires the owner, Remote Duels access and matching loopback URL/host/origin. Previously this route was not feedback-gated: this change adds `REMOTE_VISION_FEEDBACK=1` on the route and suppresses the table's diagnostic caller when collection is off. Disabling the flag does not erase existing diagnostic files. The files are not publicly served by the vision asset route.

**Owner AI crop upload:** `POST /api/remote-vision/ai` accepts a bounded JPEG (at most 256 KiB, 1024×1024) and sends it and optional candidate card names to Anthropic's Messages API. It does not write images/answers to local disk or SQLite. It requires the owner, Remote Duels access, `REMOTE_VISION_AI=1` and an API key; this change additionally requires `REMOTE_VISION_FEEDBACK=1` on GET capability and POST. Provider/decoder errors are deliberately not logged because they may echo image data. Anthropic's handling is external to this repository; no claim is made here about provider retention.

Thus with `REMOTE_VISION_FEEDBACK` off, the feedback, diagnostic and AI routes all reject image collection before parsing the image body. There is **no configured video recording**, but it would be false to say that this code has no image-storage paths at all. Both feedback and diagnostics store camera-derived crops when enabled; AI can send a crop externally. Existing files can survive turning the flag off, under their own retention rules.

The development vision lab also offers explicit browser exports of labeled samples. They are user downloads, not a server upload or automatic room archive. Camera calibration/preferences live in browser `localStorage`; tap memory, recognition gallery and phone device tokens/mode use `sessionStorage`. Browser/runtime frame buffers are transient. The server also has a bounded 32 MiB/2,048-entry immutable value cache (`packages/shared/src/remote/storage.ts`); cached values may remain in RAM until eviction/restart, but reads always check that the database value still exists, so a purged room cannot be recovered through the cache API.

## Remote tournament evidence exception — 7 November 2026

B4 on `feat/remote-tournaments-b4` extends this audit; the original room/media findings above remain code-only findings. Accepted plan decisions D4/D5 permit one minimal row per pairing in `tournament_remote_evidence`, independent of the normal 24-hour room purge. Copied fields are table slug, both account IDs and seat mapping, table start/end/reason, games (number/winner/reason/end time), result events (`lp.change`, `player.concede`, `match.declare`, `match.confirm`, `undo`, `detection.mode`) with sequence/server time/account/seat and allowlisted action fields, each game's final seat LP, last face-up public board, reports (choice/note/time), and numeric detection summaries. Technical fields are nullable room ID, capture time, deletion deadline and absolute cap. The table schema is in `packages/shared/src/db/schema.ts`.

The public board allowlist covers monster and spell zones (including Extra Monster, Field and Pendulum zones), graveyard and banished. The Extra Deck itself is excluded, including face-up Extra Deck cards. Only zone, slot, public card ID/passcode/name and position are copied: no hidden cards, hands (even revealed hands), deck lists/counts, Extra/Side, card movements, raw recognition events, undo snapshots, reducer effects, camera data, images, video, voice, vision samples, spectators, phone pairing or IP. Full logs are replayed transiently to derive final LP for every finished game; undone game endings are discarded, and same-time siding resets cannot overwrite ending LP. Eliminated seats retain only their last public cards before concede/LP clears their board. Detection summaries count logged Auto/Tap duration, click/typed identifications and manual actions/corrections, plus unknown face-up public cards at each game end. Logged actions include later-undone actions; numbers describe record completeness, never detection accuracy or proof of a winner. No new permanent replay is retained.

`captureRemoteTournamentEvidence(db, tableId)` runs at table end and is exported for B3's proposal transaction. The purge safety net captures missing evidence under the same writer lock before removing a room. Existing evidence survives through `ON DELETE SET NULL`; the room still expires on its ordinary schedule. Database triggers synchronize reports/deadlines when B3 changes its durable result row, including after room purge. Evidence is deleted on the next hourly cleanup after both confirmations (within one hour), 48 hours after timeout finalization, or 48 hours after organizer decision on a dispute. Open disputes retain evidence only until decision or the absolute 14-day cap from table end. The cap applies to all evidence. Tournament cancellation deletes evidence immediately; starting a replay leaves the previous copy on its original deadline until a newly ended room replaces the per-pairing copy. Expired/cancelled copies cannot be recreated by the room purge. Account deletion explicitly removes evidence involving either paired account, including copies whose room has already gone.

The worker's existing hourly `pruneRemoteDuels` entry point also deletes evidence, independently of the room-retention environment setting. The separate evidence copy keeps its existing deadlines; full started-table history and replay are now kept indefinitely by default, independently of those deadlines. No video is recorded. The untracked privacy draft at `data/briefs/remote-duels/privacy-text-2026-11-06.md` is updated; publication and the tournament join notice belong to the launch/UI work.

## Logs, Sentry and deletion limits

Remote moves/card identities and message suffixes are stored in `remote_events`, not a separate disk log. Remote API unexpected failures flow through `remoteError()` to the shared observability adapter. WS connection logs contain socket IDs; startup/configuration logs contain ports/origin and invalid environment values. Browser recognition failures can include track IDs/error text in developer console output (`packages/vision/src/field-watcher.ts`, `web-runtime.ts`). There is no deliberate camera-frame/video logging in these paths.

LiveKit Docker stdout is persisted by `json-file`: production rotates at 10 MiB × 2 files, development at 2 MiB × 1. The container's log path is Docker-managed, not an app media directory. LiveKit receives IPs, room/participant identities and token metadata (including internal user/room/seat IDs). The YAML does not establish exactly which values the third-party binary logs. No runtime log inspection was done, so neither IP-free nor user-data-free LiveKit logs can be certified. The checked-in Caddy configuration does not enable a separate access-log destination; deployment/platform logs remain outside this code audit.

Sentry is enabled only with its DSN. `packages/web/src/lib/sentry.ts`, `packages/ws/src/instrument.ts` and `packages/worker/src/instrument.ts` disable default PII, request bodies, cookies, header/user collection, database query values, AI inputs/outputs and local variables; web samples traces at 5%. Shared `observability/redact.ts` scrubs sensitive structured fields, URLs, SQL and credentials. An explicitly reported **numeric internal account ID can remain** as `user.id`, together with error/stack/trace data. No Sentry replay/video/frame integration is configured. Redaction is not a guarantee against all user/card data in arbitrary exception messages: free-text card names and `/remote/<slug>` strings are not universally removed by `redactText()`. Sentry data is external error telemetry and is not deleted by room purge or this account-deletion function.

Account deletion previously anonymized remote seats and kept rooms/events. It now deletes whole rooms the user created, occupied or acted in (including a past lobby member's events), together with all room rows/unused facts, plus their spectator slots, phone rows and AI limits in other rooms. Remote-only history no longer forces an anonymized account to remain. Existing feedback account deletion removes sample rows/preferences and prunes the orphaned JPEGs after commit. Local owner diagnostic files have no account association and are not removed by account deletion; general bug-report text and external logs/Sentry have their own policies.

SQLite row deletion is logical deletion, not secure erasure of freed pages/WAL or already-created backups. Backup scripts and the existing privacy page describe separate retention (including a 14-day outer limit for retained database copies); this change does not rewrite backup archives or assert the deployed configuration. No live database or existing image directory was opened or modified for this audit.
