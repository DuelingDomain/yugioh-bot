# Owner Discord webhooks

The approved request adds owner operations with channel webhooks. The bot stays disabled (ADR 0004). Existing `OWNER_USER_IDS` is the authority; it contains application `users.id`, never Clerk or Discord IDs. No public route is added.

Waitlist alerts keep one durable record per normalized email hash. The record holds an opaque random ID, Clerk entry ID, expiry (24 hours), Discord message ID and original message payload. Local form creation and signed Clerk delivery can bind the same record before or after alert delivery. Approve and Reject URLs contain HMAC-SHA256 tokens bound to the record, decision and expiry. They contain no email, webhook credentials or Clerk secret. A dedicated 32-character-minimum key signs them.

GET only shows confirmation after the Clerk session resolves and the current owner allowlist permits the application user. POST rechecks both, verifies same origin and the signature, then atomically fixes one decision and actor. A short SQLite lease excludes concurrent requests. Transient failures permit the same decision to resume; an opposite decision is never allowed. Clerk's explicit already-invited/already-rejected responses reconcile ambiguous timeouts without another invitation. The saved result is idempotent. Discord PATCH removes the links and shows the actor. Failed edits are retried by the worker; an edit failure does not undo Clerk's result. Expired links cannot start or resume an action.

Use the existing shared REST client with the endpoints verified in installed `@clerk/backend` 3.23.0: `waitlistEntries.invite` maps to POST `/waitlist_entries/{id}/invite`, and `reject` maps to POST `/waitlist_entries/{id}/reject`. The [official error reference](https://clerk.com/docs/guides/development/errors/backend-api) establishes HTTP 409 codes `waitlist_entry_already_invited` and `waitlist_entry_already_rejected`. Only the matching code counts as a completed action. List pending with GET `/waitlist_entries?status=pending&limit=1`, caching its total for five minutes. Official citations belong in the deployment guide.

The signed-in app layout mounts a small heartbeat. It sends only a route template on entry, navigation and every 60 seconds while visible. The server validates an allowlist of templates, resolves the session and atomically permits one update per user per 30 seconds across tabs and processes. `users.last_seen_at` and `last_route` overwrite prior values. No page ID, query, fragment or browsing history is saved. Online means less than 120 seconds old. The worker clears values older than 24 hours, including while status publishing is off. Duel route labels can be resolved in the browser from existing page data only if needed; generic Duel is safe by default.

The worker uses its normal non-overlapping 60-second loop to maintain one message in a second private admin channel. Persist the message ID plus webhook hash, POST once with `wait=true`, then PATCH; recreate only on message-not-found. Bound Discord content to 2,000 characters, 25 names, escaped text and disabled mentions. Show UTC-day sign-ups, cached Clerk pending count (unknown/stale on failure), active play duels by format, today's finished play duels and active drafts. Scope game statistics to the configured community. Keep status and action-edit failures contained and credentials out of reports.

Privacy notice states that admins see names, last-seen time and app sections in Discord; only latest presence exists and it expires after 24 hours. The status message is overwritten each minute. Owner setup documents both private webhooks, Clerk signed endpoint, owner ID lookup, key generation, full environment matrix and Compose recreation for web and worker.

Verification uses only targeted integration suites with real SQLite, real HMAC/Svix/session verification and HTTP stubs at the Clerk/Discord boundary. Browser coverage runs in `packages/e2e` on a dedicated slot, with no live ports, Docker or live files. No new unit tests.
